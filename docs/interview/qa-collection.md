## A. 项目与设计（16 题）

### ★Q1. 一句话说清这个项目在解决什么问题？
广告投放的决策现在靠运营人肉跨平台对数据 + 凭经验调预算，既慢又不可审计。
这个项目把「AI 建议」做成一个**可验证、可拦截、可追溯**的流程：
模型只能在 8 个只读工具上取数，输出必须过护栏节点，执行必须过安全策略和人工审批。

---

### ★Q2. 为什么不用现成的 Agent 框架（比如 Spring AI / 自己写循环）？
用的是 **LangGraph4j**，不是「不用框架」。选它的三个理由：
1. 需要**编译态图**（`StateGraph.compile()`）而不是运行时拼 Prompt——图结构在启动时就能校验，
   还能导出 Mermaid 拓扑给运营看；
2. 需要**条件边 + 回环**：护栏不通过要能回到 planner，这是 while 循环写不干净的部分；
3. 需要**检查点持久化**接口（`BaseCheckpointSaver`），自己实现落 H2/MySQL 即可。
Spring AI 更偏「调用封装」，图编排能力弱；纯手写 ReAct 循环则会把状态、重试、护栏搅在一起。

---

### ★Q3. 为什么默认是 COPILOT 模式而不是全自动？
因为 **LLM 的错不是随机错，是自信地编**。随机错可以用重试解决，自信错只能靠人工兜底。
所以节奏是：SHADOW（只算不改，攒误报率）→ COPILOT（人审批，攒信任）→ AUTONOMOUS（才放权）。
默认值取中间态，是产品判断不是技术偏好。

---

### Q4. 这个项目你一个人做的，怎么保证质量？
四道：
1. **10 个测试类 / 31 个用例全绿**（`mvn clean test`）：图端到端、护栏越界、检查点重放、
   控制台鉴权、双人审批、海外运营、渠道凭据；
2. **合成工作区**做规模验证（32 站点 / 640 活动 / 1341 个自然日），迁移可反复重跑验证幂等；
3. **节点级遥测**：每个节点的耗时、token、工具调用都落库，异常能定位到具体节点而不是「AI 挂了」；
4. **真实运行证据**：本地已累计 78 次运行、461 次节点执行、395 次工具调用、127 万 token——
   不是「能启动就算完」，是真的被用了一轮。

---

### ★Q5. 8 个工具是怎么选的？为什么是这 8 个？
按「模型回答一个问题需要什么证据」倒推的：
- 判断趋势 → `dailyReport`
- 判断哪个国家在亏 → `countryBreakdown`
- 判断是不是素材问题 → `creativeAndLandingContext`
- 判断有没有越界 → `ruleContext`
- 判断相对水平 → `peerBenchmarks`
- 判断以前是不是被驳回过 → `historicalRuns`
- 需要参考别的活动 → `scenarioCatalog`
- 要报数字前先算一遍 → `simulateBudget`

**8 个是刻意控制的**：工具越多，模型选错工具的概率越高、上下文越贵。
每个工具都能对应到护栏或审批环节的一个具体判断，没有一个是「也许有用」。

---

### ★Q6. 为什么工具全部只读？不能直接改预算吗？
广告预算是**不可逆资源**，改错了不能 Ctrl+Z。
所以第一版刻意把写操作排除在模型能力之外：模型只能产出「建议」，写操作必须经过
`optimization_run` 审批 + `optimization_ledger` 记账。
这也让整个系统的失败模式变得可控——模型再怎么错，最多是建议错了，不会直接烧钱。

---

### Q7. 这个项目和「套壳 ChatGPT」的本质区别是什么？
三个可验证的差别：
1. **有状态机**：8 节点图 + 条件边 + 反思回环，不是一次问答；
2. **有硬约束**：护栏是代码节点，四类校验越界即拦，不依赖模型自觉；
3. **有落库与审计**：检查点、遥测、审批台账三张表，能回答「它当时为什么这么建议」。

---

### Q8. 如果让你给这个项目写一份验收标准，你会写什么？
- 无模型配置时，全流程仍可跑通并明确标注来源为 `RULES` / `UNAVAILABLE`；
- 任何越界建议（幅度/符号/枚举/结构）无法进入审批队列；
- 服务重启后，未完成的 run 能按 thread 找回检查点；
- 一次运行的全部节点、token、工具调用可在控制台查；
- 合成工作区迁移重复执行，人工数据零改动、种子数据零重复。

---

### ★Q9. 最大的技术风险是什么？
**模型输出的不可控性 × 预算的不可逆性**。这两个乘起来，一次幻觉的代价可能是真金白银。
缓解是纵深防御：提示词约束 → 结构化输出 → 护栏节点 → 安全策略 → 人工审批 → 台账复核。
任何一层都可能失效，所以不能只靠一层。

---

### Q10. 为什么不用 RAG / 向量库？
因为这里要查的是**结构化指标**（某天某活动的 spend/ROAS），不是语义相似文档。
SQL 比向量检索更准、更便宜、可解释。真正需要语义的地方是「找相似历史活动」，
那确实是向量库的场景，但当前用「近 5 次审批记录」这个结构化近似已经够用。

---

### Q11. 你怎么证明护栏真的有效？
三层：
1. 单测直接构造越界 JSON，断言图走到 `self_reflect` 而不是 `finalize_plan`；
2. 遥测里 `guardrail_critic` 节点的 `REFLECT` 状态可统计，能看到拦截率；
3. 端到端：把预算幅度填成 50% 提交，观察被拒。
**注意**：这是「拦截有效性」，不是「建议质量」。质量评估需要人工标注集，目前没做，这是已知短板。

---

### ★Q12. 项目里最不满意的地方？
检查点是整图快照，状态一大 `state_json` 就会膨胀；`evidenceRefs` 目前是弱约束（靠提示词 + 人工看），
没有在代码里校验引用是否真实命中工具返回。
这两个都是「先能跑，再优化」的取舍，不是没意识到。

---

### Q13. 如果要把这个项目交给别人维护，你会先补什么？
1. 补齐「图拓扑变更指南」——新增节点要同步改哪些地方（状态字段、遥测、测试）；
2. 把护栏规则从硬编码提成配置表，支持运营自己加规则；
3. 建离线评估集（50 条历史建议 + 人工判定），改提示词前后跑回归。

---

### Q14. 为什么单体而不是微服务？
数据强关联（活动 → 报表 → 素材 → 规则 → 审批），拆开就是分布式事务；
团队规模 1 人，拆了只有运维成本没有收益。
但**已经预留了拆分点**：数据源路由是动态多租户的，智能体编排和 CMS 之间的接口是清晰的。

---

### Q15. 你的代码里最「讲究」的一处设计是哪个？
`effectiveLimit()`：`max(0, min(用户请求幅度, 规则上限))`，再叠安全策略，三层取最小。
一行代码体现了整个系统的价值观——**默认最保守，谁能放开谁显式放开**。
被问到时可以直接打开 `AdvisoryTools.java:158-160`。

---

### Q16. 这个项目上线了吗？真实数据多少？
没有上线，是个人项目，跑在本地合成工作区：库里 **640 个活动**（PASS 256 / ARCHIVE 320 / AUDITING 32 / REJECT 32）、
32 个站点、27,124 行报表覆盖 1,341 个自然日、842 篇文章。
合成数据用来验证规模行为和正确性，**不用来证明投放效果**。
如果要上线，缺的是真实渠道凭据、效果评估集和灰度方案——这三样不是代码问题。

---

### ★★Q16b. 你说测试全绿，具体测了什么？怎么 mock 大模型？
`mvn clean test` → 10 个类 31 个用例，0 失败 0 错误 0 跳过。分层：

| 层 | 怎么测 |
| --- | --- |
| 图状态机 | `LangGraphCommercialAgentTest` 起真实 Spring 上下文（`agent-sim` profile、内存 H2），用 `DynamicPropertyRegistry` 注入本地回环模型桩（`cms.agent.local-model-port`），断言状态流转、结构化字段、护栏结果与落库副作用，**不 assert 模型文案** |
| 护栏 | `AgentGuardrailsAndReplayTest` 直接构造越界 JSON（幅度超限、符号不匹配），断言图走到 `self_reflect` 而不是 `finalize_plan` |
| 检查点 | 重复写入同一 checkpoint，断言 `MERGE` 后行数不增（幂等） |
| 鉴权 | `ConsoleAuthorizationTest` 走 MockMvc，断言未签名/越权路径返回 401/403 |
| 审批 | `StaffWorkflowTest` 用 operator 提单、reviewer 审批，断言角色边界 |
| 业务算法 | `OverseasOperationsTest`（11 个用例）、`PlatformEconomicsTest` 纯计算，无外部依赖 |

**关键取舍**：不测「AI 说得对不对」（没有评估集，也不该在单测里赌模型输出），
只测「系统在模型输出好/坏/挂掉时行为是否正确」。这就是为什么这 31 个用例 0 失败且稳定。

## B. 智能体与 LLM（14 题）

### ★Q17. 讲讲你的图拓扑。
```
START → intake_context
  ├─ 无模型 / RULES_ONLY → rule_baseline → guardrail_critic → finalize_plan → END
  ├─ DEEP → research_specialist ⇄ tool_executor → strategy_planner ⇄ tool_executor
  └─ STANDARD → strategy_planner ⇄ tool_executor
               planner → guardrail_critic
guardrail_critic ─ 违规 → self_reflect → planner（回环，最多 1 次）
                 └ 通过 → finalize_plan → END
```
8 个节点，`maxIterations=24` 防死循环，工具轮次上限 5，反思上限 1。

---

### ★Q18. 为什么把「护栏」做成节点，而不是在拿到结果后 if 判断？
三个原因：
1. **可见**：护栏在拓扑图上是一个节点，运营能看懂流程，而不是一段藏在 service 里的校验；
2. **可回环**：只有做成节点，才能用条件边把「违规」路由回 planner 形成反思闭环；
3. **可观测**：护栏节点的 `REFLECT` / `OK` 状态进遥测，拦截率可统计。
如果在拿到结果后 if 判断，就只能丢弃或放行，无法让模型自我修正。

---

### ★Q19. self_reflect 具体做了什么？为什么只做 1 次？
把护栏的违规原因（例如「changePercent=35 超出允许上限 ±20%」）作为 UserMessage 追加进 planner
的历史，并禁用工具（迫使模型直接输出修正后的 JSON），然后边回到 planner 重新生成。
只做 1 次的原因：第 2 次修正的边际收益很低，且延迟和 token 成本线性增长；
如果一次修正还不行，说明模型能力不足，应该降级到规则而不是继续烧钱。

---

### ★Q20. 结构化输出怎么保证格式？
四层：
1. 提示词里给出完整 JSON 模板 + 字段约束；
2. 解析前 `stripFences` 剥离 Markdown 围栏；
3. 取首个 `{` 到末个 `}` 做子串，Jackson 解析，失败则退化为「文本分析」而不是报错；
4. 解析成功后，字段合法性由护栏节点兜底（枚举/幅度/符号）。
**没有用 JSON Schema 强约束**（部分兼容接口不支持 `response_format`），这是兼容性代价。

---

### Q21. 温度设多少？为什么？
默认 0.2（本地模型路径），可由渠道密钥里的 AI 配置覆盖。
广告预算决策要的是**稳定可复现**，不是创意发散；创意文案生成才需要更高温度。

---

### ★Q22. 多轮对话的记忆怎么存的？
Copilot 图按 `sessionId` 管理：历史消息转成 LangChain4j 的 `UserMessage` / `AiMessage` 序列，
会话落 SQL（不是内存 Map），刷新页面能恢复。
每次 turn 独立建 `CopilotTools` 实例，避免不同会话互相污染。

---

### Q23. 工具调用失败了怎么办？
统一转成 `{"available":false,"reason":"..."}` 返回给模型，**不抛异常中断图**。
这样模型能知道「这个数据拿不到」，从而在结论里说「缺少证据」，而不是编一个。
如果工具不存在，也返回 `available:false` 而不是抛错。

---

### ★Q24. 怎么控制 LLM 成本？
四个阀门：
1. 工具输出截断 6500 字符；
2. 历史审批只取近 5 次；
3. 每节点记录 input/output token，成本可归因；
4. `maxLlmCallsPerDay` 默认 200，超限直接拒绝。

---

### ★Q25. 怎么防提示词注入？
这是这个项目**做得不够**的地方，得诚实说。目前靠：
1. 工具全只读（注入也改不了预算）；
2. 输出必须过护栏（注入让它输出越界值也会被拦）；
3. 系统提示词约束「不得编造工具未返回的数据」。
但工具返回的**数据内容**（比如文章标题、用户评价）如果被注入，模型仍可能被带偏。
正确做法是工具返回值做结构化白名单 + 对文本字段做摘要而非原文注入——这一版没做。

---

### ★Q26. 什么是 Function Calling？你的实现和它的关系？
Function Calling 是模型侧能力：模型输出一个「我要调用 tool_x，参数是 {...}」的结构化请求，
由宿主执行后把结果作为 tool 消息回灌。
本项目用 LangChain4j 的 `@Tool` 定义工具、`LC4jToolService` 生成 tool specifications 并执行；
LangGraph4j 的 `tool_executor` 节点就是这个「执行后回灌」的环节，并额外做了截断和异常降级。

---

### Q27. 为什么优化图要分 STANDARD 和 DEEP 两种模式？
DEEP 多一个 `research_specialist` 节点，先做一轮「归因研究」（并行取多维证据），
再把摘要交给 planner。适合复杂归因（多国家、多素材、疑似异常）；STANDARD 适合日常快查。
代价是 DEEP 多 1-3 轮工具调用和一次模型调用，所以做成显式选择而不是默认。

---

### Q28. 模型切换后效果不一致，怎么处理？
当前靠三样：结构化输出契约（字段固定，格式差异被吸收）、护栏（数值越界一视同仁）、
遥测（按 `model_name` 分组的耗时与 token 可对比）。
**没做的是**：同一输入的模型 A/B 效果对比——需要评估集，前面说过这是短板。

---

### Q29. Agent 的死循环怎么防？
三重：`MAX_TOOL_ROUNDS=5`（工具轮次）、`MAX_REVISIONS=1`（反思次数）、
`compiledGraph.setMaxIterations(24)`（图总迭代）。
任一到顶，图必然走到 `finalize_plan` 或降级，不会无限跑。

---

### Q30. 流式输出怎么做的？
两处：
1. **节点级流式**：图执行时通过 `compiledGraph.stream(...)` 逐节点拿 `NodeOutput`，
   每个节点 `telemetry.recordNode(...)` 落库并发 SSE 事件（node/done）；
2. **文本流式**：Copilot 对话通过 SSE 推送 `answer` 事件，前端逐字渲染。
SSE 超时 180 秒，迟到订阅会先回放历史节点。

---

## C. 架构与工程（10 题）

### ★Q31. 为什么用 SSE 而不是 WebSocket？
场景是**服务端单向推送**（节点进度、token 流），客户端不需要发消息。
SSE 是纯 HTTP、浏览器自带重连、无需额外协议升级，实现和运维都更轻。
WebSocket 适合双向高频（协作编辑、行情），这里用不上。

---

### ★Q32. SSE 的连接泄漏怎么防？
三处钩子都挂清理：`onCompletion` / `onTimeout` / `onError`；
`publish` 时发送异常就把该 emitter 从 `CopyOnWriteArrayList` 移除，
列表空了把整个 runId key 移除。
订阅结构是 `ConcurrentHashMap<String, List<SseEmitter>>`，读多写少，用 COW 列表避免读时加锁。

---

### ★Q33. 检查点为什么用 `MERGE` 而不是 `INSERT`？
LangGraph4j 可能对同一节点重复写检查点（重试、重放），
`INSERT` 会产生重复行导致 `get()` 取到脏数据。
`MERGE ... KEY(thread_id, checkpoint_id)` 是 H2 的 upsert 语法，天然幂等；
MySQL 对应 `INSERT ... ON DUPLICATE KEY UPDATE`。

---

### Q34. 数据源多租户怎么做的？
动态数据源路由：按请求上下文（站点/租户标识）选择对应的 `DataSource`，
用 `AbstractRoutingDataSource` 的思路在 `lookupKey` 时决定。
本地模式只有一个 H2，路由退化为单库；生产 profile 才真正生效。

---

### Q35. 前后端怎么部署？为什么不分离？
前端产物（Vite build）直接放进 `src/main/resources/static/`，打进 JAR。
好处：部署只有一个文件，没有 Node 运行时、没有跨域、没有 Nginx 反代配置。
代价：前端改动要重新构建 + 重新打包，适合「后端为主、前端轻迭代」的项目；
如果前端要独立发版，就应该拆出去。

---

### Q36. 本地零依赖怎么做到的？
`local-cms` profile：H2 文件库 + 建表脚本 + 幂等迁移生成合成数据 + 本地签名密钥自动生成。
不需要 MySQL、不需要 Redis、不需要任何渠道 Key。
启动脚本还做了端口检测（防重复启动）、PID 落文件、后台 VBS 启动。

---

### ★Q37. 怎么保证迁移不破坏用户数据？
迁移只改「种子语料」：条件是 `article_id LIKE 'afs-article-%' AND partner = 'AFS Media'`。
手工建的活动、文章、素材、规则、凭据、导入的历史归档一律不碰。
并且迁移幂等：重复执行不会产生重复行（先按特征清理旧种子再插入）。

---

### Q38. 日志和密钥怎么管？
密钥：渠道凭据与 AI 凭据 AES-GCM 加密落库，密钥文件与业务库分离存放；
`AiModelGateway.redact()` 把 apiKey 替换成 `[凭据已隐藏]`，保证异常栈和前端不泄露。
日志：logback 分文件（stdout/stderr 分开重定向），启动结果写 `log/start.log`。

---

### Q39. 双人审批怎么实现的？
`@ConditionalOnProperty(cms.agent.require-staff-login=true)` 才启用 Spring Security；
两个内存账号 `operator` / `reviewer`（BCrypt），启动时校验长度与差异；
`POST /cms/agent/runs/*/review` 只授 `REVIEWER`，其他写接口授 `OPERATOR`；
`STATELESS` + HTTP Basic，CSRF 仅对 JSON 的 agent 写接口豁免。

---

### Q40. 如果流量涨 100 倍，瓶颈在哪？
按顺序：① LLM 调用（外部配额与延迟，最硬）→ ② 报表聚合 SQL（已建 `ad_resource_id + report_date` 索引）
→ ③ SSE 长连接数（单机 emitter 数量）→ ④ 单库写入。
对应手段：LLM 加队列 + 缓存同参结果；报表走预聚合/物化视图；SSE 换 Redis Pub/Sub 扇出；
库先读写分离，再考虑分表。

## D. 广告业务与算法（10 题）

### ★Q41. eCPM 是什么？怎么算？
`eCPM = pCTR × pCVR × TargetCPA × 1000`，即「千次展示的期望收入」。
排序用它而不是出价，是因为平台要最大化收入。
项目里 BiddingAgent 用它做出价基准，再乘动态倍率（ROAS 好 ×1.3，差 ×0.6），
并封顶在 TargetCPA 的 80%。

---

### Q42. ROAS 和 ROI 的区别？
ROAS = 收入 / 广告花费（只算广告口径）；ROI = (收入 − 成本) / 成本（含商品成本、履约等）。
广告优化盯 ROAS，因为它是投放可控的那部分；能不能赚钱还要看毛利。

---

### Q43. 为什么出价要封顶在 TargetCPA 的 80%？
留 20% 的安全垫：转化成本有波动，出价顶满时一旦 CVR 下滑就会立刻超成本；
80% 是「还能拿到量」与「不会爆成本」的折中。
这是启发式规则，不是最优解——严格最优需要知道预算约束下的边际 CVR 曲线。

---

### Q44. 预算重分配为什么用注水（water-filling）？
因为边际收益递减：把预算全给 ROAS 最高的活动，它的边际 ROAS 会迅速下降。
注水法的做法是「按边际 ROAS 降序逐档填充，最后一档等比例切分」，
等价于在总预算约束下最大化总收益的 KKT 条件。
项目里输出 `BudgetAllocation`（当前/最优/差额/历史 ROAS），并受 ±20% 调幅上限约束。

---

### Q45. 归因窗口是什么？为什么要做转化延迟修正？
用户点了广告，可能 3 天后才下单。归因窗口就是这个「算账的期限」（如 7 天点击 / 1 天浏览）。
窗口没走完的数据会**低估**转化，所以要按历史延迟分布做修正，否则会误杀还在爬坡的活动。

---

### Q46. 同期群（cohort）分析解决什么问题？
解决「不同时间进来的用户不能混着看」。按 `campaignId + cohortDate + ageDay` 存累计收入，
D1/D7/D30 看留存曲线。项目里的硬规则：重复观测**替换**而不是累加，未观测的 D7/D30 留空。

---

### Q47. A/B 测试怎么判断显著性？
CTR 是比例指标，用双样本比例 z 检验：
`z = (p1 − p2) / sqrt(p(1−p)(1/n1 + 1/n2))`，`p` 是合并比例。
多组比较要做 **Bonferroni 校正**（α/m）控制假阳性——代码里是 `adjusted = p × max(1, arms−1)`，
与 `0.05` 比较，等价于把阈值收紧到 α/m。
项目里的硬规则：周期不一致或样本不足（每臂点击与未点击各 ≥10、目标曝光 20000）**不判胜**——
宁可说「还不能判断」，也不给假结论。

---

### Q48. 素材疲劳怎么量化？
看 CTR 随时间的衰减率。项目里用「衰减曲线」拟合，输出疲劳指数；
触发条件是 CTR 持续低于基线一定比例。注意区分**疲劳**（同一素材效果衰减）
和**受众饱和**（频次过高），前者换素材，后者扩人群或降频。

---

### Q49. 为什么 Tier-3 市场只给内容套利类站点？
因为高客单服务（种植牙、保险、法律）在低购买力市场转化极差，
而内容套利类（生活、清洁、居家安全）靠流量差价，Tier-3 的 CPM 低反而有利。
项目里按垂类分配市场梯队，CPM 基线随梯队走（Tier1 约 8-9，Tier2 约 5-6，Tier3 约 2）。

---

### Q50. 多币种怎么处理？
按每日汇率折算成 USD 展示，汇率表由运营录入（日期 + 来源 + 1 USD 对应目标币种数量）。
硬规则：**未录入币种显示「缺少汇率」，不用固定默认值**——用默认值会把错误的数字变得看起来很对。
换算只影响展示，不改原始数据。

---

## E. Java / Spring / 数据库（10 题）

### ★Q51. `@Component` + 构造器注入 vs 字段注入？
全部用构造器注入：依赖不可变（`final`）、启动即暴露循环依赖、单测可手写构造。
字段注入（`@Autowired` 在字段上）会让类脱离容器就无法实例化，测试只能上 Mockito。

---

### ★Q52. 图的对象是单例，为什么还能并发跑多个 run？
图实例（`CompiledGraph`）是单例且无状态；
每次执行的**可变状态**放在 `ConcurrentHashMap<String, RunSession>` 里按 `runId` 隔离，
节点通过 `state.runId()` 反查自己的 session。
`finally` 里移除，避免内存泄漏。

---

### Q53. `ConcurrentHashMap` 为什么不能存 null？
因为它用「值为 null」表示「不存在」来支持 `computeIfAbsent` 等原子语义；
允许 null 值会让 `get()` 返回 null 时无法区分「没这个 key」和「值是 null」。
这也是为什么 `activeSessions.remove()` 不需要判空。

---

### ★Q54. 事务边界画在哪？
画在「一次业务写操作」上，比如审批通过 + 台账记账要在同一个 `@Transactional` 里；
跨节点的图执行**不开大事务**——LLM 调用可能几十秒，长事务会长时间占用连接。
所以图执行是「多次短事务」，最终一致性靠状态机与检查点保证。

---

### Q55. 事务什么情况下会失效？
① 同类内部方法调用（不走代理）；② 方法非 public；③ 异常被 catch 没抛出；
④ 抛的是受检异常而默认只回滚 RuntimeException；⑤ 数据库引擎不支持事务（MyISAM）。
项目里审批逻辑都放在独立 Service 的 public 方法上，避免①②。

---

### Q56. MyBatis 的 `#{}` 和 `${}` 区别？
`#{}` 是预编译占位符（`?`），防 SQL 注入；`${}` 是字符串拼接，只用于动态表名/列名这类
无法参数化的位置，且必须白名单校验。
项目里所有用户输入走 `#{}`，排序字段这类走枚举映射，不用 `${}` 拼。

---

### ★Q57. 索引怎么设计的？
高频聚合查询 `WHERE ad_resource_id = ? AND report_date BETWEEN ? AND ?`，
建 `(ad_resource_id, report_date)` 联合索引——等值在前、范围在后，符合最左前缀。
另外报表表数据量大时用覆盖索引（把 SELECT 的列都放进索引）避免回表。

---

### Q58. 为什么用 H2 还能跑 MySQL 语法？
H2 开 `MODE=MySQL` 兼容模式，支持大部分 DDL/DML 习惯写法。
但**不是 100% 兼容**：比如 `MERGE ... KEY()` 是 H2 的 upsert 写法，MySQL 要用
`INSERT ... ON DUPLICATE KEY UPDATE`；分页、函数名也有差异。
项目里靠「同一套 schema 两套方言脚本 + 集成测试跑 H2」来控风险。

---

### Q59. 乐观锁用在哪？
活动预算更新用版本号（或 `updated_at` 比对）：
`UPDATE ... SET budget = ?, version = version + 1 WHERE id = ? AND version = ?`，
影响行数为 0 说明被并发改过，重试或报冲突。
广告预算是「多运营同时改会出事」的典型场景。

---

### ★Q60. 分布式锁用在哪？怎么实现的？
定时同步任务（报表拉取）的防重复执行。**但要说清楚：名字叫分布式锁，实现是 DB 行锁表。**
`DistributeLockService` 走 `DistributedLockMapper`：`insertIgnore(lockKey)` 保证 key 唯一，
`tryLock(key, val, expireAt)` 带过期时间抢占，`tryUnLock` 先比对 val 再释放（防误删别人的锁）。
为什么不用 Redis：项目要求「零外部依赖可跑」，而这个锁的竞争强度是**定时任务级**的，
一天几次，DB 行锁完全够用；引入 Redis 只多一个必须保证一致性的组件。
代价也要说：DB 锁在事务里会长时间占用行锁，超时窗口靠 `expireAt` 兜底，
真要上多实例高并发应换 `SET NX PX` + Lua 或 Redisson 看门狗。
**加分细节**：这个类里的日志文案还残留着 `Failed to unlock redis lock`——历史遗留，
面试时主动说「这是从 Redis 版本改过来的，文案没清」，比被问出来好。

## F. 编码题（5 题，详解见 `coding-challenges.md`）

### ★Q61. 手写一个滑动窗口限流器（线程安全）。
要点：`Deque<Long>` 存时间戳 + `synchronized` 或 `ReentrantLock`；
每次请求先踢掉窗口外的，再判长度。
注意：单机内存版在多实例下不成立，要换 Redis（`ZSET` + `ZREMRANGEBYSCORE`）。

### ★Q62. 手写请求签名（排序取头 + MD5 + 时间窗 + nonce）。
要点：`TreeMap` 保证顺序；时间窗 12 分钟；nonce 用 `ConcurrentHashMap.putIfAbsent` 原子占位，
过期清理。**注意**：MD5 只作摘要，不是加密。

### ★Q63. 给定总预算和若干活动的历史 ROAS，写预算注水分配。
要点：按 ROAS 降序、逐档填满、最后一档按剩余预算等比例切分；
输出要带上「是否被 ±20% 上限截断」的标记。

### ★Q64. 写一个方法，判断逐日 ROAS 是上升/下滑/持平。
要点：前半段与后半段分别求 `sum(revenue)/sum(spend)`（注意是**加权**，不是比值的平均）；
`BigDecimal` 避免浮点误差；样本 < 2 天返回「样本不足」。

### ★Q65. 设计一个按 runId 的 SSE 事件总线。
要点：`ConcurrentHashMap<String, List<SseEmitter>>`；订阅时回放历史事件；
发送失败即剔除；无订阅者时零开销（提前 return）；run 结束后发 `done` 并 complete 所有 emitter。
